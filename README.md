# Makecom

Личное приложение с общей библиотекой: генерация карточки компании, ручное редактирование и утверждение, создание трёхстраничного сайта, превью и скачивание JSON/ZIP.

Требования к проекту: [scope-of-work.md](scope-of-work.md).

## Реализованные возможности

✅ — реализовано; ◐ — частично или требует дополнительной проверки; ☐ — не завершено.

| Статус | Возможность | Объём реализации |
|---|---|---|
| ✅ | Генерация компании | Германия, small/medium, бренд, направление, тип сервиса, случайный выбор из каталога, выбор модели |
| ✅ | Карточка компании | Контакты, CEO и два руководителя, история, аудитория, продукт и пять FAQ; отдельный редактор и утверждение версии |
| ✅ | Генерация сайта | AI HTML/CSS, три страницы, RU/DE, стиль, метаданные и favicon; источник фактов — снимок утверждённой карточки |
| ✅ | Библиотека и экспорт | Поиск компаний, версии сайтов, открытие/скрытие превью, JSON и ZIP; правки карточки не меняют прежние сайты |
| ✅ | OpenRouter | Поиск моделей, бесплатный фильтр, сессионный ключ, лимиты ключа, этапы, ошибки, повторы и бюджет операции |
| ✅ | Локальные данные | SQLite и JSON через общий IStorage; транзакционный импорт JSON → SQLite и сохранение после перезапуска |

| ◐ | Содержание и перевод | Правила фактов и различий заданы до генерации; пользователь принял реальные результаты. Полная независимая сверка двух компаний, RU/DE и адаптивности не завершена |

Подробные критерии: [чек-лист требований](docs/acceptance-checklist.md). Требования к смыслу задаются модели до запроса; техническая обработка ответа не гарантирует достоверность каждого факта или перевода.

## Запуск локально

Проверенная среда разработки: Node.js 24.15 и npm. Команды выполняются из корня проекта, если не указано иначе.

1. Установите зависимости: `npm ci`.
2. Если `server/.env` ещё нет, скопируйте `server/.env.example` в `server/.env`. Не перезаписывайте существующую конфигурацию.
3. Для работы без внешних сервисов задайте:
   ```env
   PORT=3000
   NODE_ENV=development
   STORAGE_DRIVER=sqlite
   DATA_DIR=./data
   MOCK_LLM=true
   OPENROUTER_SPEND_LIMIT_PER_OP_USD=0.10
   APP_BASE_URL=http://localhost:3000
   ```
4. Выполните `npm run dev`. Откройте адрес Vite из терминала, обычно http://localhost:5173. Если порт занят, Vite выберет следующий. API работает на http://localhost:3000; фронтенд обращается к нему через Vite proxy.

Mock-режим проверяет интерфейс и сохранение данных: компании тестовые, сайты шаблонные, запросов генерации к модели нет. Каталог моделей может загружаться из публичного API OpenRouter без ключа.

Для реальной генерации установите `MOCK_LLM=false`, перезапустите сервер, откройте «Подключение» и введите ключ OpenRouter. Он хранится в зашифрованной HttpOnly cookie сессии; в .env его добавлять не нужно.

Порядок в приложении: создайте компанию → откройте карточку → проверьте/сохраните правки → отметьте проверку фактов → утвердите карточку → создайте сайт. Правки снимают утверждение; прежние сайты остаются неизменными. JSON доступен и для черновика. Просмотр сохранённых результатов не вызывает генерацию.

## Сборка и проверки

```sh
npm run build
npm run start -w server
```

После сборки сервер раздаёт интерфейс и API на http://localhost:3000. Отдельный Vite для этого не нужен.

```sh
npm test
npm run typecheck
```

`npm run typecheck` проверяет клиент и сервер. Линтер не настроен. Серверная сборка очищает только свой dist, чтобы удалённые исходники не оставались в старом JavaScript. Тесты используют подменённые ответы провайдера, а не платные генерации. В ограниченной песочнице Windows тестовым сокетам/атомарной записи может понадобиться разрешение среды.

## Логи и диагностика

Сервер пишет однострочный JSON в stdout/stderr: запуск/остановка, HTTP-статус и длительность, начало/этапы/повторы/итог генерации, HTTP-статус OpenRouter и ошибки записи журнала. Успешные `/health` не засоряют вывод. На Render записи доступны в Logs; локально — в терминале сервера. Отдельного файла логов и ротации приложение не создаёт.

HTTP-ответ содержит `X-Request-ID`, события генерации — `operationId` из истории операций. В логи не записываются ключи, cookie, заголовки, URL с параметрами, тела запросов, промпты, ответы модели и содержимое карточек. Неожиданные ошибки не выводятся вместе с сырыми объектами/stack trace. Для диагностики ошибки используйте время, статус, этап и служебный ID; журнал операций хранит отдельные сведения о расходах.

## Где хранятся данные

Доступны три адаптера: `sqlite` — локальная БД, `file` — совместимость с прежними JSON-файлами, `supabase` — необязательный облачный вариант. Шаблон конфигурации использует SQLite; существующий server/.env автоматически не меняется.

При `STORAGE_DRIVER=sqlite` файл по умолчанию — `DATA_DIR/makecom.sqlite`. Можно задать абсолютный `DATABASE_PATH`. Используется встроенный node:sqlite, поэтому нужен Node.js 24.15+. В БД сохраняются карточки, утверждения, неизменяемые версии со снимками и файлами, результаты модулей и история операций. Supabase/Render/sing-box для этого не нужны.

При запуске через npm workspace относительный DATA_DIR обычно находится в `server/data`; точное расположение зависит от рабочего каталога процесса. Для резервной копии корректно остановите приложение и скопируйте весь каталог данных. Не копируйте только один открытый SQLite-файл: рядом может находиться WAL.

### Перенос существующей библиотеки из JSON

Не переключайте существующий файловый проект на SQLite до импорта: новая пустая БД не показывает старые JSON-карточки. Данные между адаптерами автоматически не перемещаются.

После `npm run build` сначала выполните просмотр без записи (из корня репозитория):

```sh
npm run storage:import -w server -- --source ./data --database ./data/makecom.sqlite
```

Проверьте пути/число записей, остановите приложение и примените импорт:

```sh
npm run storage:import -w server -- --source ./data --database ./data/makecom.sqlite --apply
```

Затем задайте `STORAGE_DRIVER=sqlite` в server/.env и перезапустите приложение. Команда выполняется в server, поэтому ./data здесь означает server/data; при нестандартном расположении используйте абсолютные пути. Импорт разрешён только в пустую БД, выполняется одной транзакцией и не изменяет исходные JSON. Повреждённый источник или конфликт ID останавливает перенос; при ошибке записи транзакция откатывается целиком. Старые снимки и файлы сохраняются без изменений.

## Простая архитектура

```text
Браузер: формы, библиотека, редактор, превью, ZIP
   → Express API
      → CompanyCore: сохранённые факты и утверждение
      → OpenRouter: генерация по запросу с бюджетом
      → IStorage: карточки, снимки сайтов, журнал операций
```

Компания — источник фактов. Сайт создаётся из снимка утверждённой версии; имена и контакты подставляет сервер. Требования к смыслу, разнообразию, структуре и переводу задаются модели заранее. JSON-разбор, контроль бюджета и очистка HTML/CSS — техническая обработка ответа. Подробности и точное состояние реализации: [архитектура](docs/architecture.md).

## Схема данных

| Объект | Основные поля | Назначение |
|---|---|---|
| CompanyCore | id, createdAt, updatedAt, inputs, identity, contacts, people, business, product, faq, facts, extensions, meta | Сохранённая карточка компании |
| CoreSnapshot | core, hash, createdAt | Копия карточки и SHA-256 на момент создания сайта |
| SiteVersion | id, coreId, lang, style, storagePath, createdAt, snapshot?, files?, generation? | Версия сайта; files — словарь имя файла → текст |
| GenerationOperation | id, kind, model, status, stage, timestamps, limitUsd, estimatedAttemptUsd?, attempts, resultId? | Прогресс и расходы, включая неудачные попытки |
| CompanyModuleResult | id, coreId, moduleKey, payload, snapshotHash, createdAt | Основа будущих направлений; полноценные модули ещё не реализованы |

### Пример структуры компании

Условный пример CompanyCore: значения поясняют назначение полей и не являются сведениями о реальной компании. В facts показана одна запись; приложение пересобирает весь словарь из карточки.

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z",
  "inputs": {
    "brandName": "Example Research",
    "country": "DE",
    "businessDirection": "Инвестиционные исследования",
    "b2bServiceType": "Анализ корпоративных отчётов",
    "scale": "small",
    "model": "provider/model"
  },
  "identity": {
    "brandName": "Example Research",
    "legalEntityName": "Example Research GmbH"
  },
  "contacts": {
    "city": "Город",
    "address": "Улица, дом, индекс, город",
    "phone": "Телефон с кодом страны и города",
    "email": "contact@example.com"
  },
  "people": {
    "ceo": {
      "name": "Имя руководителя",
      "title": "CEO",
      "bio": "Профессиональный опыт"
    },
    "heads": [
      {
        "name": "Имя руководителя исследований",
        "title": "Руководитель исследований",
        "bio": "Опыт анализа данных"
      },
      {
        "name": "Имя технического руководителя",
        "title": "Технический руководитель",
        "bio": "Опыт разработки"
      }
    ]
  },
  "business": {
    "history": "История основания компании",
    "specialization": "Специализация",
    "targetAudience": "Целевая аудитория",
    "clientProblem": "Проблема клиента"
  },
  "product": {
    "inputs": "Какие данные предоставляет клиент",
    "process": "Как компания обрабатывает данные",
    "result": "Что получает клиент",
    "limits": "Ограничения услуги"
  },
  "faq": [
    {
      "q": "Вопрос 1 о продукте",
      "a": "Ответ 1, согласованный с описанием продукта"
    },
    {
      "q": "Вопрос 2 о продукте",
      "a": "Ответ 2, согласованный с описанием продукта"
    },
    {
      "q": "Вопрос 3 о продукте",
      "a": "Ответ 3, согласованный с описанием продукта"
    },
    {
      "q": "Вопрос 4 о продукте",
      "a": "Ответ 4, согласованный с описанием продукта"
    },
    {
      "q": "Вопрос 5 о продукте",
      "a": "Ответ 5, согласованный с описанием продукта"
    }
  ],
  "facts": {
    "identity.brandName": {
      "key": "identity.brandName",
      "value": "Example Research",
      "source": "core"
    }
  },
  "extensions": {},
  "meta": {
    "version": 1,
    "approval": {
      "version": 1,
      "approvedAt": "2026-01-01T00:00:00.000Z"
    }
  }
}
```

У черновика нет meta.approval. Утверждение относится к meta.version; после изменения карточки оно снимается. Поля brandName, businessDirection, b2bServiceType и model в inputs необязательны. В people.heads всегда два руководителя, в faq — пять пар. extensions зарезервирован для будущих модулей.

Состав CompanyCore:
- inputs: country (сейчас DE), scale (small/medium), опциональные brandName, businessDirection, b2bServiceType, model.
- identity: brandName, legalEntityName.
- contacts: city, address, phone, email.
- people: ceo и ровно два heads; каждый содержит name, title, bio.
- business: history, specialization, targetAudience, clientProblem.
- product: inputs, process, result, limits.
- faq: ровно пять объектов q/a.
- facts: словарь атомарных фактов {key, value, source}; пересобирается из карточки.
- extensions: объект для будущих модулей; в JSON-экспорте пустой.
- meta: version и необязательный approval {version, approvedAt}. Без утверждения текущей версии карточка — черновик.

Типы: `server/src/core/types.ts`, `server/src/storage/types.ts`, `server/src/services/operations.ts`; схема карточки: `server/src/validators/core-schema.ts`. Источник точных ограничений — код, а не пример из старого документа.

Стоимость попытки бывает подтверждённой OpenRouter, оценочной по токенам или неизвестной после сетевого сбоя. Неизвестная сумма не считается нулём. Поле остатка лимита ключа не обязательно равно балансу всего аккаунта.

На странице «Подключение» лимиты ключа загружаются автоматически после сохранения и при открытии существующей сессии: общий лимит, остаток, расходы за день/неделю/месяц, период сброса и доступная бесплатная квота. Есть ручное обновление; недоступные значения обозначаются явно. Удаление ключа очищает эти сведения.

## Конфигурация

Шаблон конфигурации: `server/.env.example`. Главные настройки:
- OPENROUTER_SPEND_LIMIT_PER_OP_USD — серверный максимум бюджета; пользователь может понизить его в форме.
- LLM_MAX_RETRIES — общее число попыток, не число дополнительных повторов; LLM_REQUEST_TIMEOUT_MS — таймаут.
- Dev proxy в client/vite.config.ts настроен на порт API 3000; при изменении PORT нужно изменить и target прокси.
- SESSION_SECRET — отдельный секрет шифрования cookie; в production обязателен, 32+ символа. В development без него cookie перестанут читаться после перезапуска.
- APP_ACCESS_PASSWORD — пароль личного приложения; в production обязателен, 16+ символов. Basic auth принимает произвольное имя пользователя и этот пароль.
- OPENROUTER_PROXY_URL — необязательный прокси только для OpenRouter. По умолчанию используется прямой HTTPS.

Ключи не передаются в файлы сайтов, экспорт или журнал операций. .env, данные, SQLite-файлы и логи не коммитятся.

## Запуск на Render + Supabase

Render запускает один Node.js-сервис: Express раздаёт собранный клиент и API с одного адреса. Отдельный хостинг фронтенда и Vite в облаке не нужны. Supabase хранит данные в PostgreSQL, файлы сайтов — в приватном Storage bucket. SQLite и Supabase реализуют общий `IStorage`: бизнес-код работает одинаково, а физическая структура хранения отличается. Выбор задаётся `STORAGE_DRIVER`; синхронизации между базами нет.

1. Создайте проект Supabase. В SQL Editor последовательно выполните `supabase/migrations/202610250001_personal_workspace.sql` и `202610250002_generation_operations.sql`. Они создают таблицы и приватный bucket `sites` с ограничениями доступа.
2. Получите URL проекта и серверный `service_role` API key. Он нужен только серверу Render; не передавайте его в клиент, GitHub или OpenRouter-поле.
3. Откройте Render → New → Blueprint, выберите репозиторий и ветку main. Конфигурация читается из корневого `render.yaml`. Проверьте выбранные регион и тариф перед созданием сервиса.
4. Заполните `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `APP_ACCESS_PASSWORD` (16+ символов). `SESSION_SECRET` генерируется конфигурацией. Остальные настройки уже заданы: Node.js 24.15, production, Supabase, реальная генерация и бюджет $0.10 на операцию.
5. Render выполняет `npm ci --include=dev && npm run build`, затем `npm run start -w server`. Корневой каталог сервиса — корень репозитория. Порт передаёт Render; приложение слушает `0.0.0.0`. Адрес приложения берётся из `RENDER_EXTERNAL_URL`, если явно не задан `APP_BASE_URL`.
6. Откройте HTTPS-адрес сервиса. Для Basic auth используйте любое имя пользователя и настроенный пароль. В «Подключении» введите OpenRouter-ключ: он хранится только в зашифрованной session cookie браузера. Проверьте карточку, утверждение, сайт, превью и ZIP; перезапустите сервис и убедитесь, что результаты сохранились.

`/health` используется Render для проверки процесса. Успешный health check не подтверждает доступ к Supabase и OpenRouter: это проверяется реальными сценариями после развёртывания. По умолчанию используется прямое соединение с OpenRouter. Если оно не работает, сначала исследуйте ответ провайдера и сетевую ошибку, прежде чем добавлять прокси.

По умолчанию файловая система Render временная: локальные данные теряются при рестарте/развёртывании. Поэтому эта конфигурация использует Supabase. Для SQLite на Render нужен постоянный диск и путь БД на нём; текущий blueprint этот вариант не настраивает. См. [развёртывание Express](https://render.com/docs/deploy-node-express-app) и [постоянные диски Render](https://render.com/docs/disks).

Новый Supabase-проект начнёт с пустой библиотеки: локальные JSON/SQLite автоматически туда не переносятся. Для сохранения текущей библиотеки в облаке потребуется отдельный проверенный перенос данных и файлов; существующий импорт работает только из JSON в SQLite.
